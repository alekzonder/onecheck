# onecheck на Go — дизайн

Дата: 2026-11-23. Статус: на согласовании. Проверен ревьюером.

Пометка **[моё решение]** — выбор сделан автором документа, а не заказчиком;
его можно менять без пересмотра остального.

## 1. Зачем

`onecheck` — утилита для серверов: по YAML-конфигу прогоняет набор проверок
(файлы, HTTP, команды) и сообщает, всё ли в порядке. Конфиг пишет человек,
запускает cron или systemd timer. Позже появится отдельный сервис нотификаций,
который будет забирать у `onecheck` события «упало» / «восстановилось» и
рассылать их по своим правилам. Поэтому `onecheck` сам, независимо от модулей,
отслеживает переходы состояния каждой проверки.

## 2. Цели, не-цели, анти-цели

Цели:

- Один бинарник `onecheck` + модули проверок как отдельные исполняемые файлы,
  которые подхватываются без пересборки и перезапуска чего-либо.
- Единый движок сравнения в ядре: модуль только собирает данные.
- Отслеживание переходов pass ↔ fail с порогами «N подряд», очередь событий
  на диске.
- Установка и обновление модулей и самого `onecheck` из GitHub Releases.
- Понятный `--help`, документация в `docs/`, `make build` и `make check`.

Не-цели (в этой версии не делаем):

- Отправка событий по HTTP (будет позже; формат события проектируем с учётом).
- Сам сервис нотификаций.
- Собственный планировщик и интервалы на правило: разная частота — это разные
  конфиги и разные строки cron. **[моё решение]**
- История результатов: хранится только последний результат каждого правила.
- Windows. Целевые платформы: linux/amd64, linux/arm64; darwin собирается для
  разработки. **[моё решение]**
- Криптографические подписи релизов: проверяем только sha256 из
  `checksums.txt` того же релиза (целостность, не подлинность). **[моё решение]**
- Glob-шаблоны путей в модуле `file`.

Анти-цели (провал, даже если «работает»):

- Модуль, у которого своя логика сравнения, отличающаяся от ядра.
- Потерянный переход состояния: событие должно либо лежать в очереди, либо
  запуск должен завершиться ошибкой.
- Обновление, оставляющее полуустановленный бинарник.

## 3. Рассмотренные подходы

**Как подключаются модули**

1. Нативные Go-плагины (`.so`, `plugin.Open`) — так сделано в заготовке
   `0devs/onecheck`. Отклонено: плагин и ядро обязаны быть собраны одной
   версией Go с идентичными зависимостями, нужен CGO, нет статической сборки;
   «совместимость версий» вырождается в «точное совпадение сборки».
2. **Отдельный исполняемый файл на модуль, запуск на одну проверку, JSON через
   stdin/stdout — выбрано заказчиком.** Версионируется протокол, модули
   обновляются независимо, писать можно на любом языке.
3. Долгоживущий RPC (hashicorp/go-plugin, gRPC). Отклонено: избыточно для
   короткого запуска из cron, тяжёлые зависимости.

**Где живёт движок сравнения**

1. **В ядре; модуль возвращает значения полей — выбрано заказчиком.** Новый
   оператор сразу работает со всеми модулями, конфиг проверяется без запуска
   проверок. Цена: содержимое файла / тело ответа идёт через pipe, нужен лимит
   размера.
2. Go-библиотека внутри каждого модуля. Отклонено: расхождение поведения между
   версиями модулей, сторонним модулям не на Go пришлось бы писать движок заново.

**Где живут модули**

1. **Монорепо: `onecheck` и модули `file`, `http`, `command` в одном
   репозитории, один релиз — выбрано заказчиком.** Сторонние модули — любые
   репозитории с ассетами по тому же шаблону имён.
2. Репозиторий на модуль. Отклонено: четыре репозитория и CI с первого дня.

## 4. Обзор архитектуры

```
cron/systemd ─▶ onecheck run
                  │ 1. читает конфиг + include-каталоги
                  │ 2. находит модули в каталоге модулей, describe
                  │ 3. на каждое правило: запускает onecheck-<module> check
                  │      stdin: params + нужные поля   stdout: значения полей
                  │ 4. движок сравнения → pass / fail / error
                  │ 5. обновляет состояние, при переходе пишет событие
                  │ 6. пишет результат, печатает вывод, exit-code
                  ▼
   results/<rule>.json   state/<rule>.json   events/<id>.json   log
```

Репозиторий (Go-модуль `github.com/alekzonder/onecheck`, актуальный стабильный
Go). Раскладка пакетов — на усмотрение исполнителя, но с такими границами:

- `cmd/onecheck` — CLI ядра.
- `cmd/onecheck-file`, `cmd/onecheck-http`, `cmd/onecheck-command` — модули.
- `pkg/module` — публичный SDK модуля: типы протокола и хелпер `module.Main`,
  чтобы модуль на Go был «описание + функция сбора полей».
- внутренние пакеты: конфиг, движок сравнения, раннер, состояние/события,
  результаты и вывод, менеджер модулей (GitHub), ротация, логирование.

Код из заготовки `0devs/onecheck` не переносится (другая архитектура), Python-код
в этом репозитории удаляется полностью.

Библиотеки **[моё решение]**: `cobra` (CLI), `yaml.v3`, `tidwall/gjson` (пути
в JSON), `santhosh-tekuri/jsonschema` (JSON Schema), логирование — стандартный
`log/slog`. Исполнитель может заменить на равноценные.

## 5. CLI

```
onecheck [run]            запустить проверки (run — команда по умолчанию)
onecheck validate         проверить конфиг, не запуская проверок
onecheck module list      установленные модули, версии, совместимость
onecheck module search <owner/repo>...        релизы и найденные в них модули
onecheck module install <owner/repo> [name[@version]]...
onecheck module update [name...]              без аргументов — все
onecheck module remove <name>...
onecheck self-update [--version X]            обновить сам onecheck
onecheck logrotate [--logs] [--events]        без флагов — и то, и другое
onecheck version
```

Глобальные флаги: `-c, --config <path>`, `--log-level debug|info|warn|error`.

Флаги `run`:

- `-o, --output text|json` (по умолчанию `text`);
- `--only-failed` — показывать только fail/error (иначе — все правила);
- `--rule <name>` (повторяемый), `--tag <tag>` — запустить подмножество.

Поиск конфига, по очереди: `--config` → `$ONECHECK_CONFIG` →
`/etc/onecheck/config.yaml` → `$HOME/.config/onecheck/config.yaml`. Не найден —
ошибка с перечислением проверенных путей.

Exit-коды:

| Код | Смысл |
|---|---|
| 0 | все запущенные правила прошли |
| 1 | хотя бы одно правило в `fail` или `error` |
| 2 | `onecheck` не смог отработать: ошибка всего конфига, блокировка, запись результатов |

Exit-код отражает сырой результат этого запуска, а не подтверждённое
состояние. **[моё решение]**

Каждая команда и флаг имеют описание и пример в `--help`.

## 6. Конфиг

```yaml
name: main                    # обязательное имя конфига, [a-z0-9][a-z0-9_.-]*

log:
  level: info                 # флаг --log-level важнее
  dir: /var/log/onecheck
  format: text                # text | json
  rotate:                     # правила для onecheck logrotate
    max_size: 10MB
    keep: 5
    max_age: 30d
    compress: true

paths:
  modules: /usr/lib/onecheck/modules
  results: /var/lib/onecheck/results
  events:  /var/lib/onecheck/events
  state:   /var/lib/onecheck/state

include:                      # относительные пути — от каталога конфига
  - conf.d/*.yaml

events:
  ttl: 24h                    # просроченные удаляет onecheck logrotate

run:
  parallel: 4                 # одновременных проверок
  max_field_size: 10MB        # лимит значения одного поля от модуля

defaults:                     # для правил, где не указано
  timeout: 30s
  fail_after: 1
  pass_after: 1

modules:
  repos:                      # где module update/search ищет по умолчанию
    - alekzonder/onecheck

rules:
  - name: api-health          # уникально, [a-z0-9][a-z0-9_.-]*
    module: http
    tags: [api]
    enabled: true
    timeout: 10s
    fail_after: 3
    pass_after: 2
    params:                   # вход модуля
      url: https://example.com/health
    check:                    # что должно быть истинно (движок ядра)
      status: 200
      body:
        json:
          assert:
            - { path: status, equals: ok }
```

Умолчания каталогов **[моё решение]**: для root — как выше; для обычного
пользователя — `$HOME/.local/state/onecheck/{results,events,state,log}` и
`$HOME/.local/lib/onecheck/modules`.

**Имя конфига** обязательно и разводит данные разных конфигов на одном
сервере (решение заказчика): результаты лежат в `<paths.results>/<name>/`,
состояние — в `<paths.state>/<name>/`, лог — в `<log.dir>/<name>/onecheck.log`.
Имена правил уникальны в пределах одного конфига. Каталог событий общий для
всех конфигов — у сервиса нотификаций одна очередь; имя конфига входит в имя
файла и тело события. **[моё решение]** Каталог модулей общий.

В `state/<name>/` записан путь конфига-владельца. Если тот же `name` заявляет
другой файл конфига — запуск отказывает с кодом 2 и называет оба пути.

Include-файлы содержат только ключ `rules:`; подключаются в лексикографическом
порядке; дубль имени правила — ошибка конфига с указанием обоих файлов.
Неизвестные ключи — ошибка (защита от опечаток). В строках `params`
подставляются переменные окружения `${VAR}` (для токенов), неопределённая
переменная — ошибка. **[моё решение]**

Ошибки при `run` делятся на два уровня (согласовано с заказчиком):

- ошибка всего конфига — невалидный YAML, нет `name`, дубль имени правила,
  неизвестный ключ верхнего уровня — код 2, проверки не запускаются;
- ошибка одного правила — модуль не установлен или несовместим, `params` не
  проходят схему, неизвестное поле или оператор в `check`, неопределённая
  `${VAR}` — это правило получает статус `error` с текстом ошибки, остальные
  выполняются. Такой `error` участвует в состоянии как провал, поэтому после
  `fail_after` запусков уйдёт событие `fail`.

`onecheck validate` показывает все ошибки обоих уровней сразу и при любой из
них завершается кодом 2. Он проверяет: синтаксис, имена, что модуль установлен и
совместим, `params` по JSON Schema из `describe` модуля, что поля в `check`
существуют у модуля, операторы и их аргументы корректны.

## 7. Протокол модулей (версия 1)

Модуль — исполняемый файл `onecheck-<name>` в `paths.modules`. Модули ищутся
только там (не в `$PATH`). Каталог сканируется при каждом запуске, поэтому
только что установленный модуль виден сразу.

**`onecheck-<name> describe`** → stdout:

```json
{
  "protocol": 1,
  "name": "http",
  "version": "1.2.0",
  "description": "HTTP/HTTPS requests",
  "params_schema": { "type": "object", "required": ["url"], "...": "..." },
  "fields": {
    "status":   { "type": "number",   "description": "HTTP status code" },
    "body":     { "type": "string",   "description": "response body" },
    "duration": { "type": "duration", "description": "total request time" }
  }
}
```

Типы полей: `string`, `number`, `bool`, `object`, `array`, а также `bytes`
(число байт) и `duration` (секунды, дробные). Для двух последних движок
понимает в конфиге литералы `10MB` и `1h`.

**`onecheck-<name> check`**, stdin:

```json
{ "protocol": 1, "rule": "api-health", "params": { "url": "..." },
  "fields": ["status", "body"], "max_field_size": 10485760, "timeout_ms": 10000 }
```

`fields` — только поля, упомянутые в `check` правила: модуль не обязан
собирать остальное (не читать файл, если проверяют только размер).

stdout:

```json
{ "fields": { "status": 200, "body": "{\"status\":\"ok\"}" },
  "truncated": [], "error": null }
```

- Модуль не смог собрать данные (нет сети, нет прав) → `error: {"message": "..."}`
  и exit 0. Отсутствие объекта — не ошибка, а значение: `exists: false`.
- Ненулевой exit, невалидный JSON, превышение `timeout` (ядро убивает процесс
  с его группой) → результат правила `error`.
- stderr модуля уходит в лог ядра на уровне debug.
- Поле длиннее `max_field_size` обрезается и попадает в `truncated`; проверка
  обрезанного поля даёт `error`, а не тихий fail/pass. **[моё решение]**

Совместимость: ядро поддерживает диапазон версий протокола (сейчас только 1).
Модуль вне диапазона: `module list` и `validate` показывают его несовместимым,
правила с ним получают `error`, установка/обновление такой версии отказывают.
Версия модуля (semver) используется только для обновлений.

## 8. Движок сравнения

`check` — отображение «путь к значению → условие». Путь — в синтаксисе gjson
относительно объекта полей модуля: `status`, `headers.content-type`.

Условие:

- скаляр — сокращение для `equals`: `status: 200`;
- отображение операторов — все должны выполняться (И);
- комбинаторы: `all: [условия]`, `any: [условия]`, `not: условие`.

Операторы:

| Оператор | Смысл |
|---|---|
| `equals`, `not_equals` | строгое равенство значений JSON (без приведения строка↔число) |
| `contains`, `not_contains` | подстрока в строке / элемент в массиве / ключ в объекте |
| `starts_with`, `ends_with` | для строк |
| `matches`, `not_matches` | регулярное выражение (синтаксис Go RE2) |
| `gt`, `gte`, `lt`, `lte` | числа; для полей `bytes`/`duration` — литералы с единицами |
| `in`, `not_in` | значение из списка |
| `exists` | `true`/`false` — наличие пути |
| `type` | `string`/`number`/`bool`/`object`/`array`/`null` |
| `length` | вложенное условие на длину строки/массива/объекта: `length: { gte: 1 }` |
| `json` | разобрать строку как JSON и проверить: `assert` и/или `schema` |

`json.assert` — список `{ path: <gjson-путь>, <операторы...> }`; `json.schema` —
JSON Schema (draft 2020-12). Блок `json` применим к любому строковому полю
(`body`, `stdout`, `content`); невалидный JSON — это fail с понятным сообщением.
Возможности gjson (`items.#`, `items.#(state=="bad")#`) покрывают подсчёты и
выборки без отдельных операторов.

Отсутствующий путь: любое условие, кроме `exists: false`, не выполнено.
Оператор, неприменимый к типу значения (например `gt` к строке), — fail с
сообщением о типе; неизвестный оператор — ошибка конфига.

Каждое невыполненное условие даёт запись:

```json
{ "path": "body", "json_path": "status", "operator": "equals",
  "expected": "ok", "actual": "degraded",
  "message": "body json status: expected equals \"ok\", got \"degraded\"" }
```

`actual` в записи обрезается до 1 KB. **[моё решение]**

## 9. Базовые модули

**file** — `params`: `path`. Поля: `exists` (bool), `type`
(`file`/`dir`/`symlink`/`other`), `size` (bytes; для каталога — рекурсивная
сумма), `age` (duration с момента изменения), `mode` (строка вида `"0640"`),
`owner`, `group` (имена), `content` (string, только для файла), `count`
(число элементов каталога, нерекурсивно), `target` (цель symlink).
Symlink: `type` и `target` описывают саму ссылку, все остальные поля — то, на
что она указывает. Битая ссылка: `type: symlink`, `target` заполнен,
`exists: false`, остальных полей нет. **[моё решение]**

**http** — `params`: `url`, `method` (GET), `headers`, `body`,
`follow_redirects` (true), `insecure_skip_verify` (false). Поля: `status`,
`headers` (объект, имена в нижнем регистре, несколько значений через `, `),
`body`, `duration`, `tls_expires_in` (duration до истечения сертификата).
Ошибка соединения/TLS/таймаут — `error` модуля.

**command** — `params`: `run` (строка, выполняется через `sh -c`) либо `argv`
(список, без shell), `env`, `cwd`, `stdin`. Поля: `exit_code`, `stdout`,
`stderr`, `duration`. Ненулевой код возврата — значение поля, а не ошибка.

Поля `duration`, `tls_expires_in`, `group`, `target` в исходном запросе не
назывались, добавлены как дешёвые и полезные. **[моё решение]**

## 10. Результаты, состояние, события

Сырой статус запуска правила: `pass`, `fail` (условия не выполнены), `error`
(проверку не удалось провести). Для состояния `error` считается как `fail`,
но в результате и событии остаётся различимым. **[моё решение]**

**Состояние** (`state/<name>/<rule>.json`, служебное): подтверждённое состояние
`pass`/`fail`, время перехода, счётчики подряд идущих pass и fail.

- Из `pass` в `fail` — после `fail_after` провалов подряд; из `fail` в `pass` —
  после `pass_after` успехов подряд. Противоположный результат обнуляет счётчик.
- Новое правило (нет файла состояния): стартовое состояние `pass`, события нет.
  Если оно падает — событие `fail` по обычному правилу `fail_after`.
- Изменение `module` у правила с тем же именем состояние не сбрасывает.
  **[моё решение]**
- Ручной запуск с `--rule`/`--tag` обновляет состояние и порождает события так
  же, как обычный. **[моё решение]**

**Результат** (`results/<name>/<rule>.json`, перезаписывается каждый запуск, и
успешные, и упавшие):

```json
{ "config": "main", "rule": "api-health", "module": "http", "module_version": "1.2.0",
  "tags": ["api"], "status": "fail", "state": "pass",
  "transition": null, "consecutive": 2, "fail_after": 3, "pass_after": 2,
  "started_at": "2026-11-23T10:00:00Z", "duration_ms": 124,
  "failures": [ { "...": "см. раздел 8" } ], "error": null }
```

Результаты и состояние правил, удалённых из конфига, удаляются в конце
успешного запуска без `--rule`/`--tag`: каталог принадлежит одному конфигу,
поэтому это безопасно. **[моё решение]**

**Событие** (`events/<UTC-время>-<name>-<rule>-<transition>.json`) пишется при каждом
переходе подтверждённого состояния:

```json
{ "id": "20261123T100200Z-main-api-health-fail", "config": "main", "rule": "api-health",
  "transition": "fail", "from": "pass", "to": "fail",
  "at": "2026-11-23T10:02:00Z", "expires_at": "2026-11-24T10:02:00Z",
  "result": { "...": "результат запуска, вызвавшего переход" } }
```

`transition`: `fail` или `recovered`. Потребитель (будущий сервис) читает файл
и удаляет его. `onecheck logrotate` удаляет события с истёкшим `expires_at`.

Надёжность: все файлы пишутся атомарно (временный файл + rename в том же
каталоге). Порядок на правило: событие → состояние → результат; если событие
записать не удалось, состояние не меняется и запуск завершается кодом 2 —
переход повторится при следующем запуске. На время `run` берётся блокировка
(`flock`) в `state/<name>/`, то есть на конфиг: разные конфиги работают
параллельно, а если предыдущий запуск того же конфига ещё идёт — сообщение в
лог и код 2.

## 11. Вывод

`text`: строка на правило (статус, имя, модуль, длительность), под упавшими —
сообщения `failures`/`error`, в конце сводка «N passed, M failed, K errors».
`json`: `{ "summary": {...}, "results": [ <результаты как в разделе 10> ] }`.
`--only-failed` в обоих форматах оставляет только `fail`/`error`; сводка
считает все правила. Результаты идут в stdout, логи и ошибки — в лог-файл и
stderr.

## 12. Логирование и logrotate

Лог пишется в `<log.dir>/<name>/onecheck.log`; уровень: флаг → конфиг → `info`.
Сообщения уровня warn и выше дублируются в stderr. **[моё решение]**

`onecheck logrotate` (ставится в cron отдельной строкой):

- логи (своего конфига): если файл больше `max_size` — сдвинуть `onecheck.log.N`, сжать при
  `compress`, удалить лишние сверх `keep` и старше `max_age`;
- события (общий каталог, всех конфигов): удалить файлы с истёкшим `expires_at` (и нечитаемые старше TTL по
  mtime).

`onecheck` — короткоживущий процесс, сигналы переоткрытия файла не нужны.

## 13. Установка и обновление

Источник — GitHub Releases. Ассеты релиза:

```
onecheck_<os>_<arch>
onecheck-<module>_<os>_<arch>
checksums.txt                  # sha256 всех ассетов
```

Версия — тег релиза (`vX.Y.Z`); в монорепо у `onecheck` и трёх базовых
модулей она общая.

- `module search <owner/repo>...` — список релизов и модулей, найденных в
  каждом по шаблону имени для текущей платформы; без аргументов — по
  `modules.repos` из конфига.
- `module install <owner/repo> [name[@version]]...` — без имён ставит все
  модули последнего релиза. Шаги: скачать во временный файл в каталоге модулей →
  сверить sha256 → выполнить `describe`, проверить имя и версию протокола →
  `chmod +x` → атомарный rename. Источник (репозиторий, версия, sha256)
  записывается в `<paths.modules>/installed.json`.
- `module update [name...]` — для каждого модуля последний релиз из его
  записанного репозитория; несовместимый по протоколу релиз пропускается с
  предупреждением.
- `self-update` — последний (или указанный) релиз `alekzonder/onecheck`, та же
  проверка sha256, пробный запуск `version` нового бинарника, атомарная замена
  текущего исполняемого файла. Модули не трогает.

Токен `GITHUB_TOKEN` из окружения используется, если задан (лимиты API,
приватные репозитории). Клиент GitHub — за интерфейсом, тесты без сети.

## 14. Сборка, проверки, релизы

`Makefile`:

- `make build` — `dist/onecheck` и `dist/modules/onecheck-{file,http,command}`
  (статически, `CGO_ENABLED=0`, версия через `-ldflags`);
- `make test` — `go test -race ./...`;
- `make lint` — `golangci-lint` с проверкой цикломатической сложности
  (`gocyclo`, порог 25, как просил заказчик) и стандартным набором линтеров;
- `make check` — формат + `go vet` + `lint` + `test`; это единственная команда
  «всё ли хорошо»;
- `make release-assets` — кросс-сборка всех ассетов и `checksums.txt`.

GitHub Actions **[моё решение]**: `make check` на push/PR; на тег `v*` —
`make release-assets` и публикация релиза.

Тесты: табличные для движка сравнения и машины состояний; загрузка конфига и
include; интеграционные — собранные модули на временных каталогах и
`httptest`; менеджер модулей на поддельном GitHub.
