Output and results

A run reports its outcome in four places:

Where What For
exit code did everything pass cron, systemd, scripts
stdout every rule, or only the failing ones; text or JSON people, pipelines
<paths.results>/<name>/<rule>.json the latest result of each rule dashboards, other tools
<paths.events>/ changes of state notifications, see State and events

Exit codes

Code Meaning
0 every rule that ran passed (also when there were no rules to run)
1 at least one rule has status fail or error
2 onecheck could not do its job: no or invalid config, unknown flag, another run of the same config in progress, results or events could not be written, the run was interrupted (SIGINT, SIGTERM); with a directory of configs, at least one of them could not run

The exit code follows the status of this run, not the confirmed state: a rule with fail_after: 3 that failed once already gives 1.

With code 2 nothing is printed on stdout; the reason is on stderr, prefixed with onecheck:. The exception is a directory of configs where only some of them could not run: the others still run and are printed, and each config that could not run is shown as an ERROR config: line (and in configs of the JSON output), see Several configs.

An interrupted run (Ctrl-C, systemctl stop, shutdown) kills the running modules together with everything they started and records nothing: no results, no state changes, no events. A half-finished check says nothing about what it was checking, so it must not produce a fail event.

Flags

onecheck run [-c <config>] [-o text|json] [--only-failed] [--rule <name>]... [--tag <tag>]...
Flag Effect
-o, --output text|json output format, default text
--only-failed list only rules with status fail or error; the summary still counts all rules
--rule <name> run only this rule; repeatable
--tag <tag> run only rules carrying this tag; repeatable
--log-level <level> override log.level for this run and also print the log at that level on stderr

With both --rule and --tag, a rule runs if it matches either. Disabled rules (enabled: false) never run.

Results are printed on stdout only. Log lines never go to stdout, so onecheck -o json | jq is safe; warnings and errors of onecheck itself go to stderr and to the log file.

Text output

PASS   passwd-sane   (file, 2ms)
FAIL   disk-usage    (command, 14ms)  [state: pass, 1/3]
       stdout: expected matches "^[0-7]\\d?%", got "91%\n"
FAIL   api-health    (http, 124ms)  [transition: fail]
       body json status: expected equals "ok", got "degraded"
       body json /checks/1/state: schema violation: value must be 'ok'
ERROR  cache-ping    (redis, 0ms)
       module "redis" is not installed in /usr/lib/onecheck/modules (see: onecheck module install --help)

4 rules: 1 passed, 2 failed, 1 errors

One line per rule: status, rule name, module and duration. Under a failing rule, one line per condition that did not hold; under an error, the reason.

The note in brackets appears when the confirmed state needs explaining:

Note Meaning
[transition: fail] this run changed the state to fail; an event was written
[transition: recovered] this run changed the state back to pass; an event was written
[transition: reminder] the state is still fail and remind_every has passed; a reminder event was written
[state: pass, 1/3] the run did not pass, but the state is still pass: 1 of fail_after: 3
[state: fail, 1/2] the run passed, but the state is still fail: 1 of pass_after: 2

Several configs

With a directory of configs (-c <dir>, or plain onecheck with configs in /etc/onecheck/, see Configuration), the rules are grouped under a header per config, == <name> <file>, and one summary covers all of them:

== main  /etc/onecheck/main.yaml
PASS   passwd-sane   (file, 2ms)

== web  /etc/onecheck/web.yaml
FAIL   api-health    (http, 124ms)  [transition: fail]
       body json status: expected equals "ok", got "degraded"

== /etc/onecheck/broken.yaml
ERROR  config: /etc/onecheck/broken.yaml: "name" is required: it separates the results, state and logs of different configs

2 rules: 1 passed, 1 failed, 0 errors; 1 of 3 configs could not run
  • A config that could not be loaded or run has no name in its header and an ERROR config: line with the reason; the exit code is then 2.
  • With --only-failed a config whose rules all passed is left out entirely.
  • With a single config file (-c <file>) there are no headers: the output is the one shown above.

JSON output

onecheck -o json
onecheck -o json --only-failed
{
  "summary": { "total": 4, "passed": 1, "failed": 2, "errors": 1 },
  "configs": [
    { "name": "main", "path": "/etc/onecheck/config.yaml" }
  ],
  "results": [
    { "config": "main", "rule": "passwd-sane", "status": "pass", "...": "..." }
  ]
}

summary always counts every rule that ran. configs lists every config that was run, with name and path; a config that could not run has an error (and an empty name if it could not be loaded) and no results. results lists the rules in config order, config after config; with --only-failed it contains only the non-passing ones (possibly []). Each element has the result format below.

# names of everything that is not fine
onecheck -o json | jq -r '.results[] | select(.status != "pass") | .rule'

# all failure messages
onecheck -o json --only-failed | jq -r '.results[] | .rule as $r | (.failures[].message, .error // empty) | "\($r): \(.)"'

Result files

After every run each rule’s result is stored at

<paths.results>/<config name>/<rule>.json

Passing and failing rules alike. There is no history: the file is replaced on each run (atomically, so a reader never sees a half-written file). The directory therefore always shows the current picture of all rules of a config.

Results of rules that were removed from the config or disabled are deleted by the next full run (one without --rule / --tag).

Result format

The same object is used in JSON output, in result files and inside events.

{
  "config": "main",
  "rule": "api-health",
  "module": "http",
  "module_version": "1.2.0",
  "tags": ["api"],
  "status": "fail",
  "state": "pass",
  "transition": null,
  "consecutive": 2,
  "fail_after": 3,
  "pass_after": 2,
  "started_at": "2026-11-23T10:00:00.123Z",
  "duration_ms": 124,
  "failures": [
    {
      "path": "body",
      "json_path": "status",
      "operator": "equals",
      "expected": "ok",
      "actual": "degraded",
      "message": "body json status: expected equals \"ok\", got \"degraded\"",
      "fields": [
        { "path": "body", "json_path": "status", "operator": "equals", "actual": "degraded" }
      ]
    }
  ],
  "error": null,
  "output": {
    "body": "{\"status\":\"degraded\",\"db\":\"timeout\"}",
    "headers": { "content-type": "application/json", "server": "nginx" }
  }
}
Key Type Description
config string name of the config
rule string rule name
module string module name
module_version string version of the module that ran; empty if the module could not be loaded
tags array the rule’s tags, [] if none
status string outcome of this run: pass, fail, error
state string confirmed state after this run: pass, fail
transition string or null the event this run wrote: fail or recovered if it changed the state, reminder if the rule stays failed and a reminder was due; else null
consecutive number how many runs in a row ended like this one (passing, or not passing)
fail_after, pass_after number the rule’s thresholds
started_at string start of the check, UTC, RFC 3339
duration_ms number how long the check took
failures array conditions that did not hold; [] unless status is fail
error string or null why the check could not run; set only when status is error
output object what the module saw, kept for diagnosis; {} if the module has no output fields or output_tail is 0. See Saved output

Each element of failures:

Key Description
path the key of check the condition belongs to, e.g. body, headers.content-type
json_path location inside a parsed JSON document, for json.assert (GJSON path) and json.schema (JSON pointer); absent otherwise
operator the operator that did not hold, e.g. equals, length gt, any, not, json, schema
expected the operator’s argument from the config
actual the value found; null if the path was missing; long values are cut to about 1 KB
message a ready-to-show sentence combining the above
fields a short list of the concrete fields behind the failure, see Failed fields; never empty for a failure onecheck writes

Failed fields

message is complete but can be long: for any, not and some it shows the whole element and the whole condition. fields names only the concrete leaf fields that decided the failure, with their values, so a notification can say briefly what is wrong. Each element:

Key Description
path full path to the field, including the element index, e.g. containers.#(state=="running")#.2.name
json_path location inside a parsed JSON document, as in the failure; absent otherwise
operator the operator applied to this field, e.g. in, equals, length gt, exists
actual the field’s value, cut like actual of the failure; null if the field is missing
missing true when the field is absent; absent otherwise

What the list holds:

Failure fields
a plain operator (equals, in, length gt, exists, json, schema, …) the field itself
every one failure per failing element and condition, each with its own field
any the failing fields of all the alternatives
not the fields the negated condition checked and that held; a missing field has missing: true
some the failing fields of every element
every/some on a path that is missing or not an array the path itself

A field that repeats (same path, json_path and operator) is listed once, and the list stops at 20 entries. For example, this rule

check:
  containers.#(state=="running")#:
    every:
      any:
        - { path: name, in: ["app-bot-1", "app-postgres-1"] }

writes, for every extra running container, a failure whose message shows the whole container and whose fields names just the one that matters:

"fields": [
  { "path": "containers.#(state==\"running\")#.2.name", "operator": "in", "actual": "smoke-tls-proxy" }
]

Saved output

A failed exit_code: 0 alone does not say what went wrong. So onecheck keeps the raw output of the check in the result, whether or not a condition uses it and whether the rule passed or failed:

Module Saved fields
command stdout, stderr
http body, headers
file nothing

Which fields are saved is decided by the module (it marks them as output, see Module protocol); how much is kept is decided by the config:

defaults:
  output_tail: 10k      # default for every rule; this is also the built-in default

rules:
  - name: backup
    module: command
    output_tail: 100k   # more for this rule
    params: { run: /opt/backup/run.sh }
    check: { exit_code: 0 }

  - name: token-check
    module: http
    output_tail: 0      # keep nothing: the response holds secrets
    params: { url: https://example.com/token }
    check: { status: 200 }
  • The size is per field and accepts k, m (1k, 10k, 1m) as well as KB, MB; a bare number is bytes.
  • A longer text is cut to its last output_tail bytes and then starts with …: the end of the output is where the error usually is.
  • A value that is not text (headers) is kept whole if it fits into output_tail and left out otherwise.
  • A command killed by its timeout still has the output it printed before that in output, next to status: error.
  • Output is cut from what the module returned, which is itself limited by run.max_field_size (default 10MB): of a larger output only the first max_field_size bytes are seen at all.

The result file is overwritten by the next run, so output always belongs to the latest run. An event embeds the result of the run that changed the state, including its output, so a notification can show why the check failed.

Saved output may contain secrets (tokens in a response body, passwords printed by a script). Result directories are created with mode 0750 and files with 0640; set output_tail: 0 on rules whose output must not be stored.
